# Reinstatement after blacklisting

**Proposed behavior for Task Node · 17 November 2026.** A blacklisted contributor gets one unpaid network task 24 hours after the blacklist entry was created. Passing it restores access automatically. Three distinct authorized operators can also restore access manually at any time. Either decision applies to one blacklist entry. The signed-in contributor can always see who needs to act next.

For example, an entry created Monday at 09:15 UTC becomes eligible Tuesday at 09:15 UTC, including when the contributor is offline. If the feature starts Wednesday, the worker offers the task on startup. The contributor opens Tasks, submits evidence, and receives either a specific request for revision or a reinstatement receipt. They never have to request ordinary network work to begin.

## What the contributor sees

Show a persistent **Account blacklisted** notice in the signed-in app and pin the reinstatement card above the Tasks tabs, including the empty and wallet-linking states. Give the contributor the recorded reason, the start time, the effect on new network tasks and task rewards, and the next step. Render timestamps in local time with the time zone. Use text for every status and announce changes to assistive technology. Render the following copy from server state.

| State | Message and action |
|---|---|
| Waiting for the first 24 hours | “Your reinstatement task will be available on [date] at [time].” Show time remaining. |
| Due and being issued | “Your reinstatement task is being prepared.” Refresh automatically. If issuance is overdue, show “Delivery is delayed. We’ll retry automatically.” |
| Wallet unlinked | Show the normal waiting or task card. The contributor can open, submit and complete the unpaid task through their signed-in account. |
| Offered or accepted | “Your reinstatement task is ready” with **Open task**, or “Reinstatement in progress” with **Continue task**. |
| Submitted | “Awaiting board review. You submitted on [date/time].” No contributor action is due. |
| More evidence needed | Show the reviewer’s reason and **Update submission** on the same task. |
| Paused | “You paused this task. Resume whenever you’re ready.” Provide **Resume task**. |
| Separate wallet restriction | “This wallet is restricted. You can still complete your reinstatement task.” Link to the account-owned task and show a reference for wallet ownership review. |
| Delayed review | “Your submission is still awaiting review. A backup reviewer has been notified.” Show the submission time and next review time. |
| Closed by manual approval | “Three operators approved your reinstatement. This task is closed.” Link to the receipt. |
| Reinstated | “Your blacklist was lifted on [date/time].” Show whether this followed task completion or operator approval. Refresh task eligibility and show any separately applicable restriction. |

An open manual override adds “Manual review · 1 of 3 approvals” (or 2 of 3). The task stays available in parallel. Only the owner sees submissions and progress. Keep the public directory limited to its existing public fields. The personal status endpoint uses the signed-in account and stays available without a linked wallet. ## Eligibility and automatic delivery

Use the database clock and the original active row in `account_blacklist`. For every source, including operator blacklists, eligibility begins at `created_at + interval '24 hours'`, inclusive. A repeat write against an active row preserves its clock. A later blacklist after reinstatement has a new entry ID and starts a new clock. The source accountability case retains its historical verdict. [Blacklist schema](../../server/db/migrations/148_value_accountability.sql) · [Creation and historical verdict](../../server/value-accountability.js)

Add a blacklist_reinstatement_cases table keyed by `blacklist_id` (foreign key and primary key), with immutable `eligible_at`, a unique task ID, review revision, state, and resolution method/time. Case states proceed from waiting to offered, working, submitted and resolved. A revision request returns a submitted case to working. Pausing moves an offered or working case to paused. Resuming returns it to working. A manual lift resolves any open state. Derive display delays from timestamps. Create the case in the blacklist insertion transaction. Backfill all active entries using their original timestamps. Reconcile missing cases at startup and each minute, then drain due cases in indexed, bounded batches ordered by eligibility. A due, deliverable case should have a visible offer within 60 seconds under healthy service. Drain an overdue backlog continuously. Logging in and refreshing are read-only. A worker restart never adds another waiting period. The existing accountability sweep runs hourly and enforces a different deadline. [Existing issuer](../../scripts/value-accountability.mjs) · [Sweep timer](../../ops/systemd/tasknode-value-accountability.timer)

Create a dedicated, non-routable reinstatement board. Issue a templated network offer directly through the existing transactional off-chain offer writer. This avoids a second eligibility decision by normal task generation, which checks the blacklist at enqueue and at execution. The dedicated issuer takes a database case ID, locks the blacklist row then the case, verifies due time and active status, and reads the owner’s current linked wallet when available. It writes the board/allocation link, stable task ID derived from the blacklist ID, offer event, projection, and case transition in one transaction. Retries return the existing offer. Ordinary capacity, badge requirements, and concurrent assignments cannot consume this one reinstatement slot. Client-controlled board IDs, work types, and offer metadata confer no issuance authority. [Offer writer](../../server/offchain-task-lifecycle.js#L395) · [Enqueue checks](../../server/repositories/network-task-enqueue.js#L40) · [Generation worker](../../server/network-task-generation-worker.js#L148) · [Capacity](../../server/repositories/network-task-capacity.js)

**Accounts without a wallet receive the same task on time.** The offer writer currently requires a subject wallet. Extend it with a transaction-scoped account-owned variant for a persisted reinstatement case, permitting an empty subject wallet and omitting monetary fields that need an address. Include the task in the owner’s Tasks response by account ID. In accept, resume, submit, and verification handlers, verify the session account against the immutable case owner before wallet resolution. A later wallet link or change preserves ownership and the task ID. Preserve the existing wallet checks on ordinary tasks. If a wallet also matches another account’s blacklist, resolve only the contributor’s entry and show the independent wallet restriction. Operators verify control through the wallet-link flow and record the ownership decision separately.

**Delivery recovery.** Schedule a wake for the earliest due entry, backed by the startup and minute reconciler. Report delayed delivery at 60 seconds past eligibility for a deliverable case. Use one transaction per case and skip locked or future-retry rows. On delivery failure, roll back that case, record the error and next attempt, and keep draining the batch. Retry after 15 seconds, then one minute, then every five minutes. Page with the case ID at five minutes. A wallet ownership conflict opens one operator work item with the same escalation as a delayed review. The contributor can continue the account-owned task. Keep evidence private to the owner and assigned reviewers.

## Task and verdict

The task asks for a link or other evidence the board can verify, a short description of the contributor’s own work, and how that work helps Post Fiat or addresses the recorded reason. Accept evidence from outside Task Node so that an account barred from ordinary assignments can still qualify. The board checks attribution, checks the evidence, and explains its verdict. An example that qualifies is a merged fix with a link and an explanation of its effect. A bare claim of effort prompts a request identifying the missing evidence. Put this standard in the versioned board prompt, and store its version, evidence revision, reviewer identity, verdict and reason. [Existing board criteria](../../ops/bm-runtime/skills/board-value-accountability/SKILL.md) · [Repository prompt policy](../../RULES.md)

Use the ordinary offer, accept and submit actions. Route submissions for this case to the assigned board reviewer. Add two explicit decisions, **reinstate** and **request revision**, separate from monetary review. Use an authenticated service credential scoped to the reinstatement board. Derive reviewer identity from the credential and reject generic CLI or user-session verdicts. Only this service may apply a verdict for the latest submitted revision of this task. An evidence request returns it to the contributor. A response increments the revision and returns it to review. A contributor may set the task aside and resume it later. Refusal or cancellation on this task means pause with a **Resume** action. Time spent waiting, including reviewer delay, never closes the opportunity. [Session-bound task actions](../../server/task-actions.js) · [Board review and verification](../../scripts/bm/writes.mjs#L81) · [Existing deadline sweep](../../server/value-accountability.js#L271)

**Review delivery.** Write a pending review item in the submission transaction, unique on case and revision. The dedicated board worker leases it for five minutes. A lost lease returns it to the queue. An accepted verdict or revision request acknowledges the item in the same transaction as its effects. At 24 hours without a decision, assign the current revision to a backup board reviewer and notify the board operator. Show the contributor the next check time. Re-escalate every 24 hours while unresolved. Queue age never counts against the contributor, and the timer itself cannot lift the entry.

Model the task as 0 PFT throughout. Exclude linked reinstatement tasks from monetary review selection, payment overrides, and reward publication even after a lift. Introduce an unpaid terminal outcome `reinstatement_completed` for the projection, allocation mirror, history, capacity predicates, and replay guards. A valid positive verdict atomically records that outcome, closes the case, and lifts the exact active blacklist entry. Report success only after commit. Ordinary parked rewards then follow their existing eligibility and retry schedule. ## Manual override

One manual override requires **three affirmative approvals from three different authorized people for the same blacklist entry**. Each person has one enrolled operator account. The initiator counts if they explicitly approve. The subject cannot approve their own case. The operator interface names the account, entry date, original reason, proposed lift reason, and current count. Before the third approval the blacklist stays active. This path also works during the 24-hour wait or when a wallet cannot be linked.

Allow one open override request per entry. Bind its immutable rationale to the request ID. A replacement rationale closes that request and starts at zero. Store votes with a unique key on (request ID, operator account ID). Derive identity from the authenticated session and an operator account-ID roster maintained one per person. Recheck roster membership at quorum. The shared board-admin token, display names, and CLI-supplied actor strings cannot establish distinct people. Replace the current one-step CLI lift with the same authenticated request/approval API. Retire the account-wide lift primitive from application callers. [Current CLI lift](../../scripts/value-accountability.mjs#L145) · [Current lift query](../../server/value-accountability.js#L122) · [Operator session pattern](../../server/hive-operator-access.js#L31) · [Shared board credential](../../server/board-admin-routes.js#L32)

Store one vote row per person and request with an active flag. Reapproval updates that row. An append-only history records each transition. Roster removal invalidates open votes until a fresh explicit vote after reauthorization. The Task Node operator administrator verifies account control and one account per human before enrollment. Show only currently valid votes in the progress count. Before resolution, an approver may withdraw their own vote and the initiator may cancel the request. Record both actions. Requests stay open until cancelled, replaced, or the entry is lifted. If fewer than three eligible people are available, show “Manual approval unavailable” to the operator and alert the roster owner. The contributor still has the task route. Roster additions require a verified, distinct person, and never import votes from another identity or request.

Both the third vote and a passing task verdict invoke one transaction. Lock blacklist entry, case and open request in that order. Check the active entry ID, owner, and either the current board verdict or three valid votes. Persist the decision, mark only that entry lifted, record actor(s), reason and time, and close outstanding work. A manual lift retires any pending task with a distinct superseded outcome. A task pass closes any open override. A repeated successful call returns the recorded receipt. A stale task, vote or verdict against an earlier episode cannot lift a newer entry. Preserve an audit trail of votes, revisions and both resolution methods.

## API and delivery checks

| Proposed interface | Contract |
|---|---|
| `GET /api/me/reinstatement` | Session owner only. Return restriction, safe reason, server time, eligibility time, stage, task ID when issued, last submission time, next action, current approvals and latest resolution. No-store. Poll on focus, at eligibility, and while issuing or awaiting review. |
| `POST /api/operator/blacklist/:entryId/overrides` | Authorized operator opens a request with a reason. Return request ID and count. Opening alone contributes zero votes. |
| `POST /api/operator/blacklist/:entryId/overrides/:id/approve` | Authenticated affirmative vote. Return count and resolution receipt when lifted. Duplicate votes return the recorded result. Unauthenticated, unauthorized and stale requests return 401, 403 and 409 respectively. |
| Operator request management | Under the same override request URL, authorized operators can GET progress, POST to its withdraw action for their own vote, and the initiator can POST to its cancel action. Completed requests are read-only. |
| Board verdict write | Internal board-scoped command takes task ID, submitted revision, decision and reason. Reject stale revisions with 409. All contributor evidence writes use existing authenticated task surfaces. |

Register route policies and serve the personal status from the same case that governs issuance and lifting. If a status refresh fails, retain the last known status, label it stale, and offer retry. A local countdown reaching zero may trigger a fetch. Only the server can publish an offer or confirm a lift. **Acceptance criteria for release**

1. With a fixed UTC clock, check one second before eligibility, exactly at 24 hours, and a three-day-old active entry at startup. Expect zero early offers and one visible offer per due entry. Include both operator and accountability entries, a lifted entry, an offline user, and a user already at capacity.
2. Race two issuers, restart before and after commit, and replay the same offer. Expect one case, task, allocation and offer event. Start with no wallet and submit through the authenticated Tasks surface. Link a wallet, relink another, and introduce a wallet restriction owned by another account. In every case the owner can finish the original task and another account cannot act on it.
3. Submit, request revision, resubmit, replay an old positive verdict, then approve the current revision. Verify the blacklist stays active until the final step, including after more than 24 hours in review. Verify one lift, zero reward publications and zero payments for this task, and ordinary network eligibility on the next request.
4. Exercise the manual route with two people, a duplicate vote, an unauthorized voter, the subject, a removed operator and a third eligible person. Only three distinct eligible votes lift the entry. Race that third vote against task approval and replay both after a new blacklist. Expect one resolution receipt for the old entry and an active new entry.
5. In browser tests, verify the status and primary action before eligibility, during delivery delay, with no wallet, while working, while waiting for review, after a revision request and after either lift. Verify refresh, reopening the app, a screen reader announcement, and no personal evidence in the public directory.
6. Break delivery for one due case while a second is ready. Verify the second receives its offer, the first retries with one task ID, and its delay alert clears on delivery. Kill the review worker after claim, then advance the clock 24 hours. Verify lease recovery, one backup assignment for the revision, visible delayed-review copy, and a single eventual verdict. Cover pause/resume, wallet conflict resolution, vote withdrawal and loss of quorum in the browser and API.

Deploy the additive schema and readers first. Switch all lift callers to the quorum-aware service before enabling the worker. On enable, backfill and run the first dispatch immediately. Track oldest deliverable case past due, age of submissions awaiting review, and resolutions by method. Page the worker owner if the oldest deliverable case remains overdue for five minutes. Pausing dispatch preserves eligibility, cases and votes for resumption. A release check should follow a seeded case through the contributor UI to the durable lift receipt and confirm that the payment ledger has zero entries for its task.
