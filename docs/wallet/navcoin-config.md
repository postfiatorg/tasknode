# NAVCoin registry and selection

The server publishes `/api/l1/navcoin/registry` after login. Each entry identifies one asset by `asset_id` / `nav_asset_id`, with its own route, PFUSDC quote source, current terms and action capabilities. `/api/l1/navcoin/config?asset_id=<id>` returns only that selected entry; a missing or unknown selection returns 404. There is no default coin and no `NAVCOIN_CONFIG_JSON` launcher override.

`server/l1/navcoin-metadata.json` contains registration asset IDs, slugs, editorial names/descriptions/methodology and retirement notices. It cannot set fees, market permissions, profile, supply, NAV, route or quote source. Adding a metadata entry only displays it if its exact asset has an active profile on the configured chain. Tickers are not identity: the mainnet-linked uppercase A666 and the historical lowercase a666 test asset are different assets.

The server uses the configured loopback `L1_HISTORY_RPC_URL`, or the authenticated `L1_RELAY_URL` transport, to read status, profiles, asset information, route registry/supply status, source settlement custody and both directions of each governed quote-source order book. Reads are sequential, cached for 15 seconds and shared across requests. A changed chain tip or mismatched asset/route/book identity rejects the read. No signer is exposed. The gallery uses this public snapshot; review and submission independently refresh relevant state and require wallet quotes, signatures, literal acceptance and verified effects.

Production defaults to disabled. `TASKNODE_L1_ENABLED` controls the navigation, direct wallet links, public coin profiles, authenticated HTTP routes and WebSocket gateway. The checked-in Fly configuration keeps it disabled. Enabling it is an operator deployment step after the relay is reachable and checked; a browser setting cannot enable server routes.

Fly requires `L1_RELAY_URL` (an HTTPS origin) and the server-only `L1_RELAY_TOKEN`. The relay runs on the host that already reaches the wallet proxy and validator tunnels, using `node server/l1/relay.js`; examples are `ops/navcoin-relay.service` and `ops/navcoin-relay.Caddyfile`. Its configuration names are `L1_RELAY_PUBLIC_ORIGIN`, `L1_RELAY_TOKEN`, `L1_RELAY_PORT`, `L1_HISTORY_RPC_URL`, `L1_WALLET_PROXY_URL`, `L1_WALLET_PROXY_ORIGIN`, `L1_WALLET_PROXY_TOKEN_FILE` (or `L1_WALLET_PROXY_TOKEN`), `L1_BRIDGE_PROXY_URL`, and `L1_BRIDGE_PROXY_ORIGIN`. The TLS proxy uses `NAVCOIN_RELAY_HOST`. Supply these through protected operator-owned files, never browser configuration or Git. The example systemd unit needs Node 24 and an installed checkout at its configured working directory; it does not restart automatically.

The relay binds to loopback. Publish only its TLS reverse proxy, preserving Host and Origin and supporting WebSocket upgrades. It requires the relay credential before allowing any route, reuses the gateway's existing read/submit and custody boundary, and separately allows the server's registry and archive reads. It cannot sign, execute governance, choose caller-provided upstreams or submit through the archive read endpoint. Its upstream proxy credential stays on the relay host; Fly only holds the separate relay credential. Existing proxy and bridge-job processes remain in place.

`L1_PROVING_WINDOW_UTC` names the daily hours in which proofs are made, and so in which Solana deposits and both withdrawal paths (Solana and Ethereum) are open, as `HH:MM-HH:MM` in UTC with the opening before the closing on the same day, for example `17:00-19:00`. It is read in one place, `server/l1/proving-window.js`, on the server that answers the browser. The three readiness answers (`/api/l1/bridge/solana/readiness`, `/withdrawals/readiness`, `/solana/withdrawals/readiness`) then carry `proving_window` with the hours and the server's clock, and the deposit and withdrawal screens say when the route opens, until when it is open, or that it should be open and is not. Unset, malformed, empty or crossing midnight: no window is announced and the screens behave as before. Change it when the proving schedule changes; it does not open or close anything itself.

`L1_ETHEREUM_RPC_URL` optionally selects the server-side mainnet provider for pool reads and publication receipt verification; the public fallback is Ethereum PublicNode. Historical transaction discovery also needs outbound HTTPS to Blockscout. `B23_ACCOUNT_EQUITY_PATH` and `B23_FEE_PLANS_PATH` are optional sanitized operator artifacts for the existing facts/issuer endpoints, not prerequisites for registry discovery or consumer trading. Do not mount brokerage credentials or raw account exports. No new database migration is introduced by this release.

Book trading is available for six-decimal, non-retired assets with an observed source-asset order book or a valid native creation route that can establish that market. An empty book does not promise a fill. Native creation/cash-in require matching finalized policy NAV, live/unpaused route, valid height/freshness, supported source custody and no external spread recipient. Amounts, wallet inventory, receiving limits and reserve capacity are checked during review. Unsupported or stale entries show the chain-derived reason, with no transaction buttons. A changed selection remounts the action screen so a previous coin's review cannot be signed under the new selection.

Native creation reserves source PFUSDC, subscribes, then releases the unused export entitlement. Each step is separately reviewed and signed. The required unused Ethereum recipient binding comes from that coin's registered route controller; this flow never exports or signs an Ethereum transaction. Cash-in is limited to the wallet's tracked subscription inventory and matching source reserve. Order-book acquisitions do not create subscription eligibility. Fees remain outside NAV as verified by actual source custody and supply deltas.

Ethereum capability currently reports the native route's registered token/controller and chain ID, with liquidity explicitly unverified. Registered addresses are not proof of deployment or usable pool liquidity. No Ethereum swap action is enabled by a metadata flag or predicted address.

The consumer entry point is NAVCoins. Its Buy and Cash in links select that asset; Market and Cash in also have a coin selector. Home values each held NAVCoin from its own finalized reading and excludes retired NAV from its total. Activity labels every registered asset and route by ID.

If the proxy reports a connection error after submission, the gateway can recover
an exact public signed envelope from the last eight committed blocks. Recovery
requires a single-transaction batch, a matching native `tx` report and a literal
accepted/rejected receipt. It only reads; it never repeats the submission. Native
selected-block verification is retained as such, without claiming a replay of the
entire historical log. Unresolved submissions remain uncertain and the wallet
instructs the user to check Activity and balances before another transaction.
